"@inkandswitch/patchwork-providers": patch
---

Adds patch layers: a patch doc changes another document without writing on it. A patch doc names its target (`on`), the target's heads when it was made (`at`), and a list of `{ path, value? }` patches. `providePatchLayers(element, { repo, folder })` lays the patch docs in a folder (skipping links marked `off: true`, which keep their place in the stack) over every document resolved beneath `element`, and stacks on top of whatever remappers sit above it. `folder` may be a promise, for a folder still being made: subscriptions are claimed at once and answered when it resolves.

`DocHandleDescriptor` gains `layers`, a front-first list of patch doc urls. When a descriptor carries layers, `OverlayRepo` backs the handle with a `LayeredDoc`: an in-memory Automerge doc showing the target with the patches applied, kept in step with the live target. Writes at or under a patched path land in the front patch covering them; every other write goes to the target. Pinned-heads urls are shown unpatched. Patch docs themselves are always found in the realm's root repo, never through a remapper, so a draft can't swap them for copies.

A patch's entries can also be text and mark entries: `{ path, text: { from, to?, insert } }` replaces a run of a string, and `{ path, mark: { from, to, name, value } }` marks one (`value: null` unmarks). Both hold their run by Automerge cursors into the target, so they move with the target's edits around them; editing inside (or right at the edge of) a patched run goes into the patch, and editing anywhere else in the string goes to the target. A text entry also notes the characters either side of its run (`around`), so when someone retypes exactly the words it replaces, it goes on replacing what now sits there (and reads as stale) instead of turning into an insert beside it. A mark entry can also go on text a patch adds: `{ within: <text entry id>, start, end }` holds offsets into that entry's `insert`, which move as it's edited; an editor marking a patched run gets its mark split between the target's text and the patch's. `patchHighlights(handle, path)` says which runs of a shown string patches decide (and what the target has there instead), following an overlay handle to the layered doc behind it, for editors to highlight. Any entry may carry its own `at`. A layered doc laid over another layered doc's overlay (a nested view's) skips the patches already showing underneath, so each patch is applied once. A patch with `record: true` takes every write that would have gone to the target, and every write over a patch laid behind it, which stays as it was: a value it puts is recorded over, and an edit to text it adds becomes a text entry in the recording patch naming the entries it was made over (`text.over`), which aren't shown while it is. New helpers: `textPatch` and `markPatch` build entries from positions; `fromAutomergePatches` turns a list of Automerge patches into entries (text indexes become cursors) and reports the ops it couldn't use; `readEntry` says what an entry changes, then and now; `isEntryStale` judges one entry.

A list with a patch on one of its indexes is worked out whole from the target's list each time it's laid, so a patch removing an item removes exactly one, the target's inserts and deletes keep the list in step, and an edit reaches what it was made on: the target's item, or the patch whose put shows there, wherever earlier patches have shifted it. `landPatch` lands text exactly as overlays show it, holds overlays laying the patch still until it has landed, and returns where each text entry's text now starts.

`OverlayRepo` takes an optional third argument, `{ scratchRepo }`, the storage-less repo layered docs live in. Also exported: `createPatch`, `isPatchStale` and `landPatch` (puts a patch on its target for real and empties it).

`@automerge/automerge` is now a peer dependency.
