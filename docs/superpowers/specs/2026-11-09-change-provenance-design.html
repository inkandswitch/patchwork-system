Change provenance

Every Automerge change made in a patchwork tab says which package version made it, so a developer can answer “which tool broke this doc?” from the doc alone.

Taken from ermine, where every write carries its actor, frame and site, and explain() reads them back. Approved in conversation with chee; this page replaces the markdown draft.
+6 Bper change on the wire, for the short key
~150 Bonce per doc per package version, for the record
~1 µsextra change() time from the message
<20 µsbudget for stack capture, not yet measured

Goal and scope

The first reader is a developer debugging a doc. They need a list of a doc’s changes with the package version that made each one, from the console. Nothing is built for anyone else yet.

In

  • A short key on every change a tab makes
  • The key’s full record, inside the doc
  • explain and explainSummary on window.patchwork

Out

  • Blame per field or text span
  • Any UI
  • Reverting one writer’s changes
  • Stamping changes made inside workers

Finding the writer

At tab setup, before any package loads, DocHandle.prototype.change and changeAt are wrapped once. @automerge/automerge-repo is a single external per realm, so the wrap covers tools, components writing through the base repo, and handles shared between views. Handle identity is untouched.

Wrapping handles per view was rejected. Components receive the base repo, not the view’s overlay core/elements/src/patchwork-view.ts:536, and repo.find returns one shared handle per doc.

  1. A tool calls handle.change(fn), directly or through a shared external such as solid-automerge.
  2. The wrapper raises Error.stackTraceLimit, captures new Error().stack, and restores the limit.
  3. It walks the frames for the first URL that belongs to a package, which skips the frames of shared externals.
  4. That package root maps to a cached key. The change runs with pw:<key> in its message.
  5. If the change landed and the doc has no record for the key yet, a second change, with the same message, writes the record.

The record names a package version, not a tool. A frame shows which package wrote, not which of its plugins.

What a change carries

  • Key: the first 8 base58 characters of a hash of the package root, computed once per root and cached.
  • Message: pw:<key>. When the caller passes its own message, the key goes on a new line after it.
  • Matching: readers use /(?:^|\n)pw:([1-9A-HJ-NP-Za-km-z]{8,})$/. The key can be longer after a collision.
// no message from the tool
"pw:4kQx9TmB"

// the tool passed { message: "rename layer" }
"rename layer\npw:4kQx9TmB"

The record

Right after a package version’s first change to a doc, a change of its own, carrying the same pw:<key> message, writes its record:

doc["@patchwork"].writers["4kQx9TmB"] = { url: "automerge:2jaGJcuHPpLmFzRxxyAQ4kZPQ5mu#7hZ5RYdE…" }
  • A change of its own, not part of the tool’s change: sub-handles call A.change themselves and never pass through the root handle’s change, so no wrapper sees the root doc inside their callback automerge-repo DocHandle.js:382-391. It also leaves a tool’s empty change empty. Revised while planning; the first draft wrote it in the same change.
  • Written only when the tool’s change landed (the heads moved). A doc without @patchwork gets { writers: { … } } created there. When @patchwork or its writers is present but not an object, the value is left as it is: the message, no record. A created @patchwork has no type. The only visible effect is in patchwork-view’s error for a doc no tool opens, which says “no tool for …” instead of “missing @patchwork metadata” core/elements/src/legacy-impl.ts:631. Revised after review; the first draft left these docs without a record.
  • Every form is stamped and recorded the same way: the callback and value forms of change, changeAt, and sub-handles, whose record goes through their root handle. A sub-handle’s remove() takes no options and stays unstamped.
  • An existing record under the key with a different url is a collision. The writer’s key then takes one more hash character until it is free, cached per doc.
  • A dev loop that rebuilds a package adds one record per rebuild that writes to the doc, about 150 B each. Accepted.

Reading it back

Two exports from @inkandswitch/patchwork, which sites put on window.patchwork so they work from the console:

explain(handle, { limit = 50, since?: Heads }): ExplainedChange[]
explainSummary(handle): { writer, count, first, last }[]

explain reads A.getChangesMetaSince(doc, since ?? []), which returns metadata without decoding ops, and lists changes newest first as { hash, time, actor, message, key, writer }.

writerWhen
{ url }The key resolved through @patchwork.writers
"unrecorded"A key with no record, because the doc’s @patchwork or writers isn’t an object
nullNo key: made before this landed, or by an unstamped writer

message is the caller’s own text with the pw: line removed, or null. explainSummary groups the rows of the whole history by writer, with a count and the first and last time each one wrote.

Testing

Vitest only. Browser coverage comes from CI’s e2e.

  • First, a stack-capture microbench. The budget is under 20 µs per change, against a ~730 µs sync round trip. Over budget, the writer gets cached per call site before anything else is built.
  • frames.ts: captured stack strings from all three engines, including frames of shared externals and the site bundle.
  • writer.ts: each URL form (main, /@/, http dev source, site), key stability, the collision suffix.
  • stamp.ts, against a real in-memory Repo with the frame source injected so a test chooses the stack: a package’s first write records it and later writes don’t; a caller’s message is kept; the value shorthand, changeAt and sub-handles are stamped and recorded; a doc without @patchwork gets one holding only writers; a non-object @patchwork or writers is left alone; handle identity unchanged.
  • explain.ts: a doc with mixed writers, changes from before this landed, since and limit.

Decided on 2026-11-09

  • First reader: debugging, “which tool broke this doc”. A console reader is enough.
  • Record home: in the doc, so collaborators can resolve keys their own tools didn’t write. Written in a change of its own right after the writer’s first change, revised while planning because sub-handles never reach the root’s change.
  • Attribution: one wrap of the shared DocHandle prototype, with the writer read from the stack.
  • Docs without @patchwork: the record creates it, holding only writers.
  • Granularity: a package version, not a single tool.
