The hub

hub/hub.ts, hub/serve.ts, hub/port-backend.ts, hub/protocol.ts

automerge-repo 3 replaces network and storage adapters with one sedimentree backend per Repo, and its IndexedDB storage allows one live backend per database. So tabs can't each be a node on a shared database, as they were on automerge-repo 2. The automerge SharedWorker is the origin's one node. It holds the SubductionBackend, with its IndexedDB (<prefix>-documents), its socket to the sync server and, on keyhive sites, keyhive. Its own small key-value database (<prefix>-hub) keeps the signer seed and keyhive's archive.

Each tab's Repo runs on a PortBackend, a sedimentree backend whose every call goes to the worker over a MessagePort that the tab hands it ({type: "hub", port}). The worker opens a session of its own for each of the tab's sessions and streams its events back, remote-heads from the server included. Tabs load automerge's wasm and nothing else. When the worker is replaced, the tab hands the new one a port: its sessions open again there (the new initial load arrives as live records, which Automerge skips), and calls nobody answered are sent again. Each tab holds a Web Lock for as long as it lives, and the worker closes a tab's sessions once it can take that lock.

A single change stored while a sync round for its document is in flight used to be lost (the round had exchanged heads already, and the push waited on a subscription the round hadn't set up yet), so a change made straight after create() never reached the server. The pnpm patch to @automerge/automerge-repo-subduction starts a catch-up round for such a store. The same patch exposes the backend's native engine for keyhive sync.

Keyhive

hub/keyhive.ts, keyline/*.ts

Keyhive (@keyhive/keyhive) is used directly, as pushwork's keyline does it, without automerge-repo-keyhive. It lives only in the worker. It syncs with the server over subduction's keyhive frames (keyline/sync.ts, keyline/wire.ts, the subduction_keyhive server's messages), and the server's contact card comes from /keyhive/contact-card. KeyhiveBackend wraps the worker's backend: blobs are encrypted on the way in and decrypted on the way out, so storage and the server only ever see ciphertext. A blob that won't open yet is held and tried again whenever keyhive learns something. New documents get keyhive-minted ids in one group per device, which the server relays. Creating one waits for a keyhive sync so the server knows the document before its blobs arrive. Tabs ask the worker about access through PatchworkHive.

That's keyhive for servers that serve their card (keyhive.ark "0.8", staging). A server still on ARK 0.6 and keyhive 0.3 ("0.6", subduction.sync.inkandswitch.com) speaks ARK's own keyhive messages, so hub/keyhive-ark06.ts uses ARK 0.6's KeyhiveSubductionAdapter and KeyhiveBlobInterceptor (@ark-0.6/automerge-repo-keyhive) over the same engine, through a shim for subduction 0.27's hex peer ids. Keyhive 0.3 has a world principal, so public documents there are read with the device's own keyhive, and there is no public pair. The two keep their state apart in the worker's database.

A device's decryption keys come from prekey secrets in its own archive, which never syncs: the same seed on a fresh device can't open what the first one wrote. A second device is a second identity, and has to be granted access.

Reading public documents

hub/public.ts, public-pair-principals.ts

Keyhive 0.6 has no public "world" user. A repo is made public to an app by granting two principals whose secrets the app ships in the clear:

reader
Read. Its archive holds its prekey secrets but no signing key, so anyone can decrypt as it and nobody can sign as it.
fetcher
Relay. Its signing seed is shipped, so anyone can connect to the sync server as it and pull the ciphertext.

The user connects as the user, who isn't a member of these docs, so the server never sends their blobs on that connection. The worker therefore connects a second time, as the fetcher, with a backend of its own (<prefix>-public-documents). It syncs keyhive as the fetcher, hands each keyhive event it hasn't handed over yet to a keyhive opened as the reader, and decrypts blobs with that. A first visit hands over every public event the server holds, thousands of them, once. The reader's archive and what was handed over are kept. A RoutingBackend opens a document on the public connection when the user's keyhive doesn't know it and the reader can read it, and on the user's otherwise. Every keyhive in the worker shares one queue, since keyhive's wasm isn't reentrant.

Nothing is written through the public connection: writes always go to the user's. Pushwork makes repos public this way (--public-access read), and the pair in public-pair-principals.ts has to be exactly the one pushwork grants, or it reads nothing already published.

The resolver

automerge-protocol-handler.ts, automerge-protocol-handler-worker.ts

The resolver is the Repo that resolves automerge: URLs for the service worker when no tab can. It lives in a SharedWorker, so one instance serves every tab and lives as long as any tab does. The worker's script takes the lock, then imports the rest.

Its Repo sits on the hub's backend directly, beside the tabs' sessions (see the hub). When the service worker can't get a tab to resolve a request that looks like an encoded URL, it broadcasts a HandoffRequestMessage on HANDOFF_CHANNEL. The resolver resolves the automerge URL, writes the response into the service worker's cache (keyed by a Request rebuilt to match the one the service worker is holding), and replies on the same channel.

Recycling the resolver

automerge-protocol-handler.ts: RECYCLE_AT_MB, RECYCLE_IDLE_MS

A wasm memory grows and never shrinks: a module holds the most it ever needed at once until its global goes. Resolving packages at boot takes the resolver's automerge to 90–130MB, and letting the documents go gives none of it back.

So once handoffs stop for RECYCLE_IDLE_MS, an instance whose wasm has grown by more than RECYCLE_AT_MB restarts itself, as it does for a new build. Tabs spawn the replacement, the service worker re-sends any handoff still unanswered, and what was resolved is in its cache, so the replacement doesn't load it all again. Since every tab's Repo now runs through the worker, it doesn't recycle while any tab is connected: each tab's sessions would all have to open again.

Starting a worker early

worker-early.ts

A module's body only runs once its whole static import graph has been fetched and evaluated, which for the automerge worker is most of a megabyte and takes from half a second to several. Until it asks for its lock, nothing can tell it exists: the service worker, finding no lock, asks the tabs to start a worker.

So a worker's script is a small module that asks for its lock and buffers the tabs' connect events, which go nowhere without a listener, then imports the rest; startWorkerControl picks it up from there. The two halves hand over through the global rather than a module, so it survives them being bundled separately (the dev server bundles each worker on its own).
