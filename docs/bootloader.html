Reading public documents

public-pair.ts, public-pair-principals.ts

Keyhive 0.6 has no public "world" user. A repo is made public to an app by granting two principals whose secrets the app ships in the clear:

reader
Read. Its archive holds its prekey secrets but no signing key, so anyone can decrypt as it and nobody can sign as it.
fetcher
Relay. Its signing seed is shipped, so anyone can connect to the sync server as it and pull the ciphertext.

The user's own Repo connects as the user, who isn't a member of these docs, so the server never sends it their blobs. Instead a second Repo connects as the fetcher. It syncs keyhive as the fetcher, hands every keyhive event it gets to a keyhive opened as the reader, and decrypts blobs with that. It sits beside the user's Repo as a peer on a MessageChannel, and the user's Repo asks it for exactly the docs the user's keyhive doesn't know, so a find for a public doc is answered over automerge sync like any other.

The reader Repo never writes: anything the user changes in a public doc stays local. Pushwork makes repos public this way (--public-access read), and the pair in public-pair-principals.ts has to be exactly the one pushwork grants, or it reads nothing already published.

The public reader's worker

public-reader.ts, public-reader-worker.ts

The public reader runs in a SharedWorker: one per origin, for as long as any tab is open. It reads public documents for every tab's Repo and for the resolver's.

It's there rather than beside each Repo because catching up on the server's keyhive is seconds of wasm. On a tab's thread that held up the page, long enough that the service worker gave up asking the tab for its own requests, and the resolver, which then got them, had to catch up all over again. Its keyhive state is kept in IndexedDB, so only the first start replays it all.

Each Repo is a client: a tab sends {type: "client", port} on the worker's port, for itself or for the resolver. A SharedWorker can't start another, so the tabs introduce the two. The reader answers on port, as PublicReader.serve does.

The resolver

automerge-protocol-handler.ts, automerge-protocol-handler-worker.ts

The resolver is the Repo that resolves automerge: URLs for the service worker when no tab can. It lives in a SharedWorker, so one instance serves every tab and lives as long as any tab does. The worker's script takes the lock, then imports the rest.

It's a node like any tab's: the same IndexedDB, its own sync-server socket, and the storage channel to the tabs. Resolving requests is its whole job. When the service worker can't get a tab to resolve a request that looks like an encoded URL, it broadcasts a HandoffRequestMessage on HANDOFF_CHANNEL. The resolver resolves the automerge URL, writes the response into the service worker's cache (keyed by a Request rebuilt to match the one the service worker is holding), and replies on the same channel.

Recycling the resolver

automerge-protocol-handler.ts: RECYCLE_AT_MB, RECYCLE_IDLE_MS

A wasm memory grows and never shrinks: a module holds the most it ever needed at once until its global goes. Resolving packages at boot takes the resolver's automerge to 90–130MB, and letting the documents go gives none of it back.

So once handoffs stop for RECYCLE_IDLE_MS, an instance whose wasm has grown by more than RECYCLE_AT_MB restarts itself, as it does for a new build. Tabs spawn the replacement, the service worker re-sends any handoff still unanswered, and what was resolved is in its cache, so the replacement doesn't load it all again. Only the resolver goes: every tab is its own node, with its own socket.

Starting a worker early

worker-early.ts

A module's body only runs once its whole static import graph has been fetched and evaluated, which for the automerge worker is most of a megabyte and takes from half a second to several. Until it asks for its lock, nothing can tell it exists: the service worker, finding no lock, asks the tabs to start a worker.

So a worker's script is a small module that asks for its lock and buffers the tabs' connect events, which go nowhere without a listener, then imports the rest; startWorkerControl picks it up from there. The two halves hand over through the global rather than a module, so it survives them being bundled separately (the dev server bundles each worker on its own).
